## 0. 為什麼挑這兩件事

站的一句話定位是「幫你決定今天穿什麼，而且買得合身」（功能規劃 v1 §0；企劃前段的三個動機：不知道該買哪個尺寸、不知道今天該穿什麼、看到穿搭找不到同款）。對照目前做到的：

| 動機 | 功能清單裡的項目 | 前台現況（第十五輪結束時） |
|---|---|---|
| 今天該穿什麼 | 6.1 天氣穿搭 `特` | 天空、頂欄、一句話列、穿搭頁都顯示「今天 18°，濕度 85%，有雨」——**但那是寫死的假資料**（`getWeather` 回常數）。穿搭頁有「今天為什麼是這套」的理由（`weatherFit.js`），首頁第一屏冷天把有外套的排前面。沒有預報、沒有「合今天」的篩選 |
| 買得合身 | 6.2 尺寸推薦 `特`、身形資料 `特` | 商品頁有模特兒試穿資訊（必做，已做）與尺寸表；**尺寸推薦、身形資料兩頁都還是佔位** |
| 找不到同款 | 6.4 穿搭照牆 `特` | 等照片來源定案（`FEATURES.wall = false`） |

三個動機，第一個做了一半、第二個沒做、第三個被外部條件卡住。所以這一輪：**子輪 1 把天氣做成真的，子輪 2 做尺寸推薦**；試穿人偶（6.5，`加`，停損 11/23）列為子輪 3，做前兩個的結果再決定。穿搭牆仍不動。

## 1. 參考與查證（2026-10-10 上網；證據狀態照 vault 規則標）

- **WEAR（ZOZO）コーデ予報**——`access-verified`：讀了 ZOZO 技術部落格〈コーデ予報の地点推定〉。確認的事：功能是「その日の天気に合わせたコーディネートを提案する」；天氣來自 WeatherNews WxTech 的 1 km 網格「体感予報」，有一個十級的「体感指数」（濕度、風速加上使用者回報），**指數決定袖長（半袖／長袖）與單品類別**；2025 年 1 月起自動取得位置，不存位置、每次重算最近的預報點。**沒確認**：畫面長什麼樣、一次推幾套。→ 借：用一個「今天要多厚」的等級決定推薦（我們已有 1–5 的厚薄等級），位置用「最近的縣市」就好。
- **tenki.jp 服裝指數**——只有搜尋摘要（`link-present`）：10–100 十級，依早／日／晚三個時段的預報溫度，級距對應單品（20 羽絨、30 大衣、40 有內裡的風衣、50 薄外套、60 長袖、70 短袖加開襟、80 短袖、90 無袖）。各家對「幾度穿大衣」的門檻不一致（WeatherNews 用 8° 以下冬衣、5° 以下羽絨；另一篇說最低溫 15° 以下）。→ 我們的 `WARMTH` 對照表（22° 以上薄……12° 以下厚）在同一個量級，不改；門檻照規劃 §5 的「天氣規則管理」由後台維護。
- **Open-Meteo**——`content-validated`：讀了 API 文件與條款，**並從這台機器實際呼叫**（臺北 25.03, 121.56：`current` 24.0°、濕度 84%、WMO 3 陰、`daily` 七天的最高／最低溫、最大降雨機率、天氣代碼；回應 1.0 KB、1.3 秒；回應標頭 `access-control-allow-origin: *`，瀏覽器可直接呼叫）。條款：非商業用途（教育內容明列可用）、每日 10,000 次、每小時 5,000 次、每分鐘 600 次以下，資料 CC BY 4.0 要標示來源。
- **中央氣象署開放資料**——功能規劃 §17 查過：觀測資料集 O-A0003-001 有氣溫、濕度、天氣現象，**要註冊取得授權碼**，缺值代碼 `-99`／`X`；降雨機率在預報資料集（未驗證）。→ 規劃 6.1 說「由後端定時抓取並快取，前台不直接呼叫、不放金鑰」是對的；Open-Meteo 免金鑰，所以**前台先直接打 Open-Meteo，後端做了 `/api/weather` 再換**（形狀一樣，見 §5）。
- **Virtusize（日本多家電商用的尺寸推薦）**——`access-verified`（新聞與產品頁的摘要）：輸入身高、體重、年齡、性別（在意的部位選填），對照數千組體型模型推估尺寸；商品端依穿著照分成「緊／普通／寬」三種版型；另有「和手邊的衣服比」——把自己有的衣服和要買的衣服疊成插圖比尺寸。→ 借：**用模特兒試穿資訊當基準**（我們每件都有「模特兒 170 cm／56 kg 穿 M」），比對照表更誠實也更好解釋；三圍有填再和尺寸表逐項比。
- **ZOZOTOWN 評論**——`link-present`：2023-11 起評論帶購買者的性別、年代、身高、體重、平常穿的尺寸與實際尺寸感。→ 我們沒有評論功能，不做；但「同身高體重的人怎麼穿」是尺寸推薦下一步最自然的資料來源，寫進契約的「加分」。
- **PAZZO 試穿報告**——那個網址 404，這次沒驗到；第十輪已做的「模特兒試穿資訊」不受影響。

## 2. 原則

1. **假的要說是假的**：抓不到天氣時退回示範值，畫面上要寫「示範天氣」；用上次快取要寫「上次 10:20 的資料」。不讓人以為那是現在的天氣。
2. **規則寫在畫面上**：推薦尺寸要說依據（「模特兒 170／56 穿 M；你 178／70，建議 L」），合今天要說為什麼（「偏薄一點，進出室內剛好」）。這是規則式推薦，發表時就叫規則式，不叫 AI（功能規劃 §15 的提醒）。
3. **不替人決定**：推薦的尺寸只標「建議」、不自動選；「合今天」是一句話列裡可以關的一格，不是強制篩選。
4. **資料形狀照契約**：前台直接打 Open-Meteo 只是過渡，`getWeather()` 回的形狀就是 `/api/weather` 的形狀。

## 3. 子輪 1：天氣真的接到穿搭

### 3.1 資料

- `src/weather/cities.js`：十四個縣市的代表座標（臺北、新北、基隆、桃園、新竹、臺中、彰化、嘉義、臺南、高雄、屏東、宜蘭、花蓮、臺東）；`nearestCity(lat, lon)` 用 haversine 找最近的。
- `src/weather/openMeteo.js`：組網址（`current=temperature_2m,relative_humidity_2m,apparent_temperature,precipitation,weather_code,is_day`、`daily=temperature_2m_max,temperature_2m_min,precipitation_probability_max,weather_code`、`timezone=Asia/Taipei`、`forecast_days=7`）、5 秒逾時、把 WMO 代碼對成站內的三種 `condition`（0–1 晴；2–3、45、48 多雲；51 以上的雨、毛毛雨、陣雨、雷雨、雪都算雨）。
- `getWeather({ city })`（`src/api/index.js`）回：

```json
{
  "city": "臺北", "cityCode": "taipei",
  "temperature": 24, "humidity": 84, "apparent": 28, "condition": "cloudy", "isDay": false,
  "observedAt": "2026-10-10T01:30:00+08:00", "fetchedAt": "2026-10-10T01:31:12+08:00",
  "source": "open-meteo",
  "stale": false,
  "forecast": [{ "date": "2026-10-10", "high": 28, "low": 24, "rainChance": 2, "condition": "rain" }, "…共 7 天"]
}
```

  順序：有 15 分鐘內的快取就用快取（`source: cache`，`stale: false`）→ 打 Open-Meteo → 失敗就用 24 小時內的舊快取（`stale: true`）→ 都沒有就示範值（`source: demo`：臺北 18°、85%、有雨、七天假預報）。快取在 localStorage `weather:<cityCode>`。
- `src/stores/weather.js`：整站一份——`weather`、`city`（記在 localStorage `city`，預設臺北）、`setCity`、`locate()`（瀏覽器定位 → 最近縣市；拒絕就不動）、`status`。開發版認 localStorage `weatherDemo`（整包覆蓋，給驗收與截圖用；正式版不認），並掛 `window.__weather.probe()`。

### 3.2 用在哪

- **一句話列的第一格**從靜態的「今天 24°C，」變成可以選的一格：「今天 24°C」／「合今天 24°C 的」→ 網址 `?fit=today`。合今天 = 這套最厚的那一層對上今天要的厚度差在 −1～+1 之間（`fitVerdict`：差 ≤ −2 會冷、−1 偏薄、0～+1 剛好、≥ +2 太厚）。假 API 的 `getOutfits({ fit })` 自己去拿天氣來篩；後端對應 `GET /api/outfits?fit=today&city=taipei`。
- **穿搭卡**多一個小標：「合今天 24°」「偏薄」「會冷」「太厚」（有天氣才出現）。
- **首頁的店多一排「這一週穿什麼」**：七天，每天一欄——星期、天氣圖示、最高／最低溫、降雨機率（≥ 30% 才寫）、一套合那天溫度的穿搭（人形、標題、連到穿搭頁）。挑法：那天的平均溫 → 要的厚度 → 差 0～+1 的穿搭裡挑（下雨優先外層不吸水的；有喜好推測就優先首選路線；七天盡量不重複（挑過的扣分；候選不夠時才會重複），不夠就放寬到差 −1）。手機橫向可滑。
- **首頁第一屏的「臺北」變成可以換的詞**：點開是縣市清單，最上面一項「用我的位置」；換了縣市，天空、頂欄、一句話列、這一週、穿搭頁全部跟著換。
- **頂欄的小字、穿搭頁的理由**改讀 store；穿搭頁的理由多「太厚」那一句。
- **頁尾**加「天氣資料：Open-Meteo（CC BY 4.0）」（條款要求；這是頁尾第二個外連，理由是授權，不是裝飾）。
- **示範或舊資料**：第一屏那行字後面加小字「示範天氣」或「上次 10:20 的資料」。

### 3.3 驗收（expand-check 新段）

用 `weatherDemo` 覆蓋成 18°、85%、有雨、七天假預報再量（結果才可重現）：一句話列第一格讀「今天 18°C」、點開有兩個選項；選「合今天的」→ 網址 `?fit=today`、套數 = 腳本用同一個 `fitVerdict` 從資料算出來的數；卡片有「合今天」「偏薄」等小標且數量和資料一致；這一週有 7 欄、每欄有人形與連結、七套不重複；換縣市（點清單選高雄）→ 第一屏與頂欄的城市變高雄、localStorage `city=kaohsiung`；穿搭頁理由含「今天 18°」。拿掉覆蓋、擋掉 open-meteo 的網路（CDP `Network.setBlockedURLs`）→ `source` 是 `demo` 且畫面有「示範天氣」；先塞一筆 2 小時前的快取再擋網路 → `source` 是 `cache`、`stale` 為真、畫面有「上次」；放開網路 → `source` 是 `open-meteo`、溫度是數字、七天預報有 7 筆（這一項靠真的網路，失敗就照實列）。

## 4. 子輪 2：身形資料與尺寸推薦

### 4.1 身形資料

- 會員 `body: { height, weight, chest?, waist?, hips?, updatedAt }`（公分、公斤；三圍選填）。契約 `GET/PUT/DELETE /api/me/body`；表 `member_body`。
- `/account/body`（會員中心第五個分頁「身形」，兩組的第一組）：四個欄位＋儲存＋清掉；說明「只用來算尺寸建議與試穿，不公開」。
- `/onboarding/body`：和偏好調查一樣可略過；**不插在調查的流程裡**（註冊後三步已經夠長），而是調查結果頁多一句「也填身形？（30 秒，尺寸建議會用到）」連過去，`?redirect=` 一樣帶著走。
- 訪客：商品頁可以臨時輸入身高體重（存 localStorage `body`，登入時併進帳號——和收藏一樣的做法；帳號有的優先）。

### 4.2 推薦規則（`src/products/sizeAdvice.js`，純函式）

1. **基準是模特兒**（每件都有 `fit: { height, weight, size }`）：身高每差 12 cm、體重每差 8 kg 各算一級，`offset = round((h − fit.height) / 12 + (w − fit.weight) / 8)`；從模特兒穿的尺寸往上下移 `offset` 級，超出範圍就取最邊的一個並說「已是最大／最小」。
2. **有三圍而且商品有對應的欄**：尺寸表的「胸寬」是平量半圍 → ×2 和胸圍比；「腰圍」「臀圍」直接比。每個尺寸算「衣服 − 身體」的鬆份；上衣外套要 ≥ 8 cm、下身腰 ≥ 2 cm、臀 ≥ 4 cm；挑鬆份最小但不小於門檻的尺寸；兩種算法不同時，**以三圍為準、附註兩個都寫**。
3. **輸出**：`{ size, basis: 'model'|'measure', fit: '偏緊'|'合身'|'寬鬆', text, alternatives }`，文字像「模特兒 170 cm／56 kg 穿 M；你 178 cm／70 kg，比模特兒高 8 公分、重 14 公斤，建議 L。想合身一點選 M。」
4. **不推的情況**：單一尺寸（F）、童裝（110–130）、沒有 `fit` 的商品、身高體重離模特兒太遠（offset 絕對值 ≥ 3）→ 只說「差距大，建議看尺寸表」。
5. 建議的尺寸沒貨 → 照說建議，另加「這個尺寸沒貨了」。

### 4.3 畫面

- 商品頁尺寸欄旁：有身形 → 一行「建議 L」加依據，尺寸選項上那個尺寸多一個「建議」小標（不自動選）；沒身形 → 「輸入身高體重看建議」展開兩個欄位，輸入後馬上算（訪客存本機）。
- 收藏頁的尺寸下拉：有建議就把建議的尺寸標出來（「M（建議）」）。
- 會員中心「身形」、偏好調查結果頁的那一句。

### 4.4 驗收

訪客在 `/products/101` 輸 178／70 → 建議 L、文字含「比模特兒高 8 公分」；輸 160／48 → 建議 S；輸 200／120 → 「差距大」；登入 demo（沒身形）→ 提示填；`/account/body` 存 168／58、胸圍 92 → 商品頁依三圍（`basis: measure`）建議且文字含「依你的三圍」；清掉 → 回到輸入提示；單一尺寸商品不顯示建議；童裝不顯示。

## 7. 驗證方式與沒辦法驗的

每個子輪：`npm run build`、`expand-check.mjs` 新段、`shop-check.mjs` 60、`member-check.mjs` 41 在 1252×699 與 390×844、`check:contrast`（新顏色要加）、`shots.mjs` 截圖看過、位元組掃描。**沒辦法驗的**：Open-Meteo 在使用者那邊的延遲與可用性（條款的配額是全站共用的上限，發表現場幾十個人同時開沒問題，大量灌會被擋）；尺寸規則對不對（沒有真人資料，是設計假設；模特兒基準至少看得懂、能被反駁）；手機實機定位的權限提示長什麼樣。
