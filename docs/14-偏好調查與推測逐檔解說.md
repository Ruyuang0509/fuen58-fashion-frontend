# 14　第十五輪・子輪 4：偏好調查、喜好推測、為你排

2026-10-06。規格在 [09](09-內容與功能拓展-規格.md) §5；使用者說「25 分鐘後開工」，設計全部自主判斷。這是第十五輪的最後一個子輪。

## 做了什麼（一句話）

註冊成功後先問三件事——給誰穿、挑三套你會穿的、看你的風格組成比例；之後站裡的穿搭預設照你的喜好排（喜歡的路線排前面，可以關），商品頁多一排「你可能也想看」附理由，首頁第一個詞用你最喜歡的路線；會員中心多一頁「我的偏好」看得到這些是怎麼算的。

## 設計怎麼定的

- **像 Spotify 第一次登入挑歌手，不像問卷。** 第 2 步是 8 套人形，點就好；每挑一套，從相鄰的兩條路線各補一套進來（挑了街頭就多一套龐克、一套戶外），越挑越看得到自己的方向。相鄰表在 `themes.js` 的 `THEME_NEIGHBOURS`，是衣櫃裡常一起出現的路線，不是隨機。
- **結果是一條比例，不是一個標籤。** 「34% 街頭・33% 戶外・33% 龐克」比「你是街頭系」誠實——沒有人只穿一條路線（功能規劃 6.3 借 Stitch Fix 的呈現）。
- **推測的來源寫在臉上。** 標題底下那一行「你挑了 3 套街頭，街頭的排前面。」、會員中心列出每條路線的理由與算法（挑的 1、收藏的 0.6、看過的 0.2），使用者看得到為什麼被排成這樣，也能一鍵關掉。
- **選了風格就不排。** 路線頁、活動頁本來就是一條路線，照喜好排沒有意義；只有首頁的店與全部穿搭會。
- **只有註冊會問，登入不會。** 老會員不被打斷；想重挑去會員中心。
- **三步都能略過。** 「先不選」「先不挑，直接開始逛」；略過第 2 步時只存給誰穿（如果有選）。
- **第 1 步的答案馬上有用：** 「開始逛」回首頁或全部穿搭時順手帶上 `?for=women`，一句話列的「給誰穿」就是選的那個。

## 逐檔

- `src/taste/profile.js`（新）：純函式。`buildProfile({ preferences, favorites, history, outfitsById, productsById, themes })` 把三種訊號加成每條路線的分數——調查挑一套 1.0；收藏一套穿搭 0.6、收藏一件單品 0.6 平分給它所屬的路線；看過一套 0.2、看過一件 0.2 平分——再用 `normaliseWeights` 變成兩位小數、總和剛好 1 的權重（最大餘數法：先捨去到 0.01，差的補給餘數最大的，平手照路線順序）。回 `{ weights, top, reasons, source }`；理由取每條路線最強的那一種訊號（「你挑了 3 套街頭」「你收藏了 2 件復古」「你最近看了 4 套戶外」）；沒有任何訊號回 `null`。`sortByWeights` 給舞台排序：權重高的先，**同權重的照路線順序排在一起**（規格寫「同權重照 id」，做出來三條交錯著看像沒排，改成同一條的放一起，再照 id）；`rankWeights` 給橫條排段。後端只存了權重、沒有名單時，用權重乘挑的套數還原。
- `src/stores/taste.js`（新）：整站共用的一份推測。從登入狀態的 `user.preferences`、收藏 store、瀏覽紀錄 store 取訊號；第一次有訊號才去要一次全部穿搭、全部單品、路線清單（要知道每套屬哪條路線、每件屬哪幾條），之後一直用。`whenReady()` 給舞台與首頁等：不然卡片會先照 id 排好、半秒後再跳成照喜好排。「照你的喜好排」的開關 `forYou` 記在 localStorage（`forYou=0` 是關；沒有這個鍵是開），存不了就只在這次有效。`savePreferences`／`clearPreferences` 打 API 之後同步更新登入狀態裡的會員資料。
- `src/views/OnboardingStyleView.vue`（新）：三步的調查。第 1 步四顆大鈕＋先不選；第 2 步的起始 8 套是每條路線一套、合「給誰穿」的優先（小孩只有一套，其他路線退回全部的）；挑一套就從相鄰路線各補一套還沒出現的、插在它後面，GSAP Flip 先記每張的位置再改資料，畫完後舊的滑到新位置、新的淡進來（系統減少動態時直接出現）；不足三套時按鈕停用，底下說「再挑 N 套就能看結果」；那一列黏在視窗底，格子越多按鈕也一直看得到。第 3 步算權重（各路線套數 ÷ 總數）、存進會員，顯示 `TasteBar`；「開始逛」回 `?redirect=`（只接受站內路徑，沒給就回首頁），「重新挑」回第 2 步保留已挑的。
- `src/components/TasteBar.vue`（新）：風格組成比例——一條橫條，每段的寬度就是百分比（flex-grow）、顏色是路線色、夠寬就寫路線名；底下一行「34% 街頭・33% 戶外・33% 龐克」。橫條是 `role="img"`，讀屏讀底下那行字。一出現從左邊長出來。調查的結果頁與會員中心都用它。

## 容易錯的地方（規格 §7 對照）

- localStorage 不能用：開關、推測的資料都退到記憶體，頁面不壞（同 cart.js 的寫法）。
- 挑的穿搭已經不在目錄：推測時略過（`outfitsById.get` 拿不到就不算），不當機。
- 「給誰穿」選小孩：童裝只有一套，起始 8 套其他路線退回全部的穿搭，不會湊不到。
- 推測來自收藏或看過的、但沒挑過：會員中心上半說「還沒挑過」，下半照常推測；`/outfits` 一樣會排、一樣能關。
- 關掉再登出登入：開關是這個瀏覽器的設定，不跟帳號走（規格這樣定；要跟帳號走就進 preferences 多一個欄位，契約 §11 可加）。
- 註冊 → 調查 → 按上一頁：回到的是註冊頁，已登入會被 guest 守衛送去會員中心，不會再註冊一次。

## 沒有驗證

- 使用者本人的手感：Flip 補進來的節奏、第 3 步橫條長出來的時間。
- 真的手機與平板；讀屏（橫條 `role="img"` 的讀法只照規格寫，沒用讀屏聽過）。
- 訊號權重 1.0／0.6／0.2 的比例是否「對」——沒有使用者資料可以校，是設計假設，寫在畫面上讓人看得到。
- 後端真的回 `preferences` 之後，登入那一刻舞台的順序有沒有閃（現在假 API 是同步的本機資料）。
