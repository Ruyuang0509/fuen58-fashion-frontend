## 1. 參考與查證（2026-10-10 上網；證據狀態照 vault 規則標）

- **Vite 的 `vite:preloadError`**——`content-validated`：讀了 vite.dev 的 Build 指南（文件版本標 v8.3.4）。動態 `import()` 載 chunk 失敗時 Vite 會在 `window` 上送 `vite:preloadError` 事件，`event.payload` 是原本的錯誤；文件的範例就是 `window.addEventListener('vite:preloadError', () => window.location.reload())`；呼叫 `event.preventDefault()` 之後那個錯誤就不會再被 throw。文件沒寫這個事件從哪一版開始有。→ 用在：部署新版本後，還開著舊頁面的人一換頁會載不到舊的 chunk 檔名——重載一次（用 sessionStorage 記住只重載一次，避免無限重載）。
- **SPA 換頁的焦點管理**——只有搜尋摘要（`link-present`；九篇來源的摘要一致，沒有逐篇開）：整頁載入會把焦點歸零並播報新標題，SPA 不會，所以要自己做；做法以「焦點移到新頁面的 h1（加 `tabindex="-1"`）」最被接受，搭配 `aria-live="polite"` 的隱藏區塊播報「已前往 X」；不要把焦點移到 skip link；Vue Router 用 `router.afterEach → nextTick → focus`。→ 照這個做；但**只在路徑改變時移焦點**，同一頁只改查詢字串（一句話列換篩選）不動焦點，否則會把鍵盤使用者從下拉格拉走。
- **台灣電商的付款期限慣例**——只有搜尋摘要（`link-present`）：搜不到蝦皮或 momo 的官方規則；摘要裡只有「待付款分頁」「賣家還沒備貨時可直接取消」這類描述。→ **15 分鐘仍是功能規劃 v1.3 的建議值**，不是抄來的慣例；畫面上寫「付款期限 HH:MM」與倒數，數字由後端定（契約 §8 的 `payBy`）。
- **axe-core**——`content-validated`（npm registry 查到 `axe-core@4.14.0` 是現行版本）：Deque 的無障礙規則引擎，在頁面裡注入後 `axe.run()` 回 WCAG 2.x A／AA 的違規清單。它只能抓自動化能抓的那一部分（約三到五成的問題；這個比例是業界常說的數字，**沒有查證**，所以不拿它當結論），讀屏實際讀起來怎樣仍要真人。
- **狀態機與訂單狀態名**——沒有新查證；沿用企劃前段 §7.2 的狀態圖與契約 §8。

## 2. 原則

1. **假的要說是假的**（沿用第十六輪）：假 API 讓物流在幾分鐘內走完是為了示範，訂單頁要寫「示範用的模擬物流」；正式版由後台更新狀態。
2. **狀態機不越線**：前台也只在對的狀態顯示對的按鈕（待付款才有「去付款」「取消」，已送達才有「確認收貨」），假 API 照契約拒絕其他轉換。
3. **錯誤不留空白**：每頁三態；全站任何沒接住的錯誤都有一個畫面可以回首頁或重試，而不是白頁或半頁。
4. **鍵盤能走完購買路徑**：從首頁到訂單完成，不用滑鼠；換頁後讀屏知道到了哪一頁。
5. **回饋不擋任務**（功能規劃 §9）：轉場短、可打斷、可跳過；減少動態時直接切換。

## 3. 子輪 1：訂單走完全程

### 3.1 假 API（`src/api/account.js`）

每次讀訂單（列表、明細、付款、取消、確認）前先「結算」（`settleOrders`，模擬後端排程）：

| 現況 | 條件 | 變成 | history 多一筆 |
|---|---|---|---|
| 待付款，付款方式不是貨到付款 | 下單超過 **15 分鐘**（`PAY_WINDOW_MS`） | 已取消 | `{ status: '已取消', at: 下單＋15 分, note: '付款逾時，自動取消' }`，`cancelReason: 'timeout'` |
| 已付款 | 付款超過 **2 分鐘** | 出貨中 | `at` = 付款＋2 分 |
| 出貨中 | 付款超過 **5 分鐘** | 已送達 | `at` = 付款＋5 分 |
| 待付款，貨到付款 | 下單超過 2 分鐘／5 分鐘 | 出貨中／已送達 | 送達那一筆 `note: '貨到付款，送達時付款'`，`payment.paidAt` 設為送達時間 |
| 已送達 | 送達超過 **7 天** | 完成 | `note: '送達 7 天後自動完成'` |

- 2 分鐘、5 分鐘是**示範用的時間比例**（真的要幾天）；7 天是功能規劃「N 天後自動」的 N，**建議值**。都寫在 `DEMO_LOGISTICS` 常數旁與畫面上。
- 貨到付款的走法是這一輪的**提案**：狀態機原圖只有「待付款 → 已付款 → 出貨中」，貨到付款的訂單在送達前本來就沒付款。提案：`待付款（貨到付款，不逾時）→ 出貨中 → 已送達（記付款）→ 完成`。寫進契約 §8 給 10/12 確認。
- `publicOrder` 多給 `payBy`（待付款且非貨到付款：下單＋15 分的 ISO 字串；其他 `null`）、`cancelReason`（`'member'`｜`'timeout'`｜`null`）、history 的 `note`（有才有）。後端照算即可，前台只顯示。
- `payOrder` 結算後才檢查：到期已取消的訂單回 `NOT_PAYABLE`「付款期限已過，訂單已取消」。
- **種子訂單的時間改成相對的**：`members.json` 的兩張訂單原本是絕對日期（9/28、10/03），有了結算規則第一次讀就會一張逾時取消、一張自動完成——示範故事就沒了。所以 `fresh()` 把種子時間整體平移：以 `2026-10-03T19:25:00+08:00`（待付款那張下單後 5 分鐘）對齊「現在」，兩張訂單的每個時間都加同一個差；資料庫多記 `seedVersion: 2`，舊版本的 localStorage 只重排這兩張種子訂單（用訂單編號認），使用者自己下的訂單不動。

### 3.2 畫面

- **訂單明細**（`OrderView`）：
  - 「訂單進度」從流水清單改成**五步時間線**：待付款 → 已付款 → 出貨中 → 已送達 → 完成；走過的步有時間、目前的步標 `aria-current="step"`、還沒到的壓淡；已取消的訂單在停住的那一步後面接一個「已取消（付款逾時／自行取消）」。貨到付款是四步（待付款 → 出貨中 → 已送達 → 完成，送達那步寫「送達時付款」）。
  - 時間線下面一行小字：「出貨與送達目前是示範用的模擬（付款 2 分鐘後出貨、5 分鐘後送達）；正式版由後台更新。」
  - 待付款（非貨到付款）：「付款期限 HH:MM，還剩 N 分」（每 30 秒重算；到期重新載入，狀態會變已取消）；「去付款」展開付款方式（信用卡沙盒、模擬付款成功；貨到付款不在這裡）→「付款」→ 成功顯示「付款完成」；「取消訂單」照舊要先確認。
  - 完成：「收到了嗎？」一段——「合身嗎？更新身形」（`/account/body`）、「拿這幾件去試穿間搭別的」（`/fitting?outer=…&top=…&bottom=…`，只帶畫得出來的三類、每類第一件）。
- **訂單紀錄**（`OrdersView`）：狀態用不同色調的小標（待付款、進行中、完成、取消四種調子，仍是文字為主、不靠顏色辨識）；待付款（非貨到付款）的列多一行「付款期限 HH:MM」；上面一排篩選「全部／待付款／進行中／完成／已取消」，狀態在網址 `?status=`，每格顯示數量。
- **訂單完成頁**（`OrderDoneView`）：待付款（非貨到付款）寫「請在 HH:MM 前付款，逾時會自動取消」並連到訂單頁付款；已付款寫「付款完成，出貨進度看訂單明細」。
- **契約 §8**：補 `payBy`、`cancelReason`、`history[].note`、貨到付款走法、自動完成的 N、以及「示範版的時間比例只在假 API」。

### 3.3 驗收（`scripts/member-check.mjs` 第 4 段重寫、加第 5b 段）

種子的待付款訂單：顯示付款期限與「去付款」→ 選模擬付款 → 已付款、時間線兩步走過；把它的付款時間改成 6 分鐘前（直接改 localStorage 的 `account`）→ 重新整理 → 已送達 → 確認收貨 → 完成 → 有「更新身形」「試穿間」連結。種子的已送達訂單：確認收貨 → 完成（舊檢查）。結帳：模擬付款那條照舊；再結一張貨到付款 → 完成頁寫貨到付款、訂單頁沒有付款期限、時間線四步 → 取消 → 已取消（自行取消）。逾時：塞一張 16 分鐘前的待付款信用卡訂單 → 列表讀到就是已取消、明細寫付款逾時。列表 `?status=cancelled` 只剩取消的。手機與桌機都跑。

## 4. 子輪 2：全站強韌化與無障礙

- **錯誤邊界**：`app.config.errorHandler` 與 `window` 的 `unhandledrejection`／`error` 接到沒處理的錯誤時，`App.vue` 改畫「出了點問題」（重試＝重新載入這一頁；回首頁），開發版把錯誤印在畫面上。路由載入失敗（`router.onError`）同一個畫面。
- **換版本後的舊分頁**：`vite:preloadError` → 這一個 session 還沒重載過就 `location.reload()` 一次；重載過還失敗才交給錯誤畫面。
- **換頁的焦點與播報**：`router.afterEach`：路徑有變（不只查詢字串）→ 下一個 tick 把焦點移到 `main` 裡第一個 `h1`（沒有就 `main` 本身，`tabindex="-1"`），並把「已前往 X」寫進一個 `aria-live="polite"` 的隱藏區塊。探索區的殼內換頁（首頁 ↔ 路線）也算路徑有變。
- **可控的失敗**（只在開發版認）：localStorage `apiFail` 寫函式名（逗號分隔，如 `getOutfits,getProducts`），假 API 那些函式就丟 `ApiError('NETWORK', …)`——拿來驗每一頁的錯誤態，也是正控（開關關掉要全綠）。
- **三態盤點**：探索區的首頁、路線、全部穿搭、活動、穿搭頁、單品、商品、品牌、試穿間、收藏、看過的，交易區的購物車、結帳、訂單、會員各頁——逐頁列「載入中／空／錯誤」各有沒有；沒有的補上（探索區的子頁 `catch` 到錯目前只是不顯示）。
- **axe-core**：加成 devDependency；`scripts/a11y-check.mjs` 用無頭 Chrome 開每一頁（含登入後的會員頁、開啟的下拉格與對話框）、注入 `axe.min.js`、跑 WCAG 2.0／2.1 A 與 AA 的規則，列出違規（規則、嚴重度、元素）；修到 0 個 serious／critical，剩的寫理由。
- **鍵盤走購買路徑**：無頭 Chrome 只用 Tab／Enter／方向鍵從首頁走到訂單完成（`Input.dispatchKeyEvent`），每一步記焦點在哪。
- 驗收：`a11y-check` 全頁 0 serious／critical；`expand-check` 加一段（錯誤態、換頁焦點、播報）；既有三支腳本不退。

## 5. 子輪 3：交易區的回饋

- **結帳兩步的連續轉場**：步驟 1 → 2 時，進度列的「2」亮起、表單從右側滑入 0.3 秒（GSAP；減少動態時直接換）；回上一步反向。表單高度變化不跳。焦點移到步驤標題照舊。
- **下單完成**：完成頁載入後播一段 1.2–1.8 秒的短動畫（訂單裡的衣服從上方落到提袋裡、提袋收口、訂單編號打出來），右上角「跳過」；動畫結束的畫面和跳過後的畫面一樣；減少動態時不播，直接顯示。
- 驗收：headless 比對「播完」與「跳過」的 DOM 相同；`prefers-reduced-motion` 模擬（`Emulation.setEmulatedMedia`）下沒有動畫元素；視覺照 claude-art 量表自檢後截圖給使用者看——好不好看是使用者的判斷。
